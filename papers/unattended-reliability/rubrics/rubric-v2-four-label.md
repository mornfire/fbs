# 一致性判据 v2：四标签优先级版

替代 v1 的四条并列定义。核心改动是**加入判定顺序与互斥规则**，让标签之间不再重叠。

---

## 一、判定顺序（必须按序，先命中者生效）

1. **NOT_RUN** — 场景只含环境、氛围或情绪描写，不含可与设定台账比对的断言。
   注意：显式标注为「假设分支 / 未发生」的内容若含可比对断言，属可检验，不进本档。

2. **UNDECIDABLE** — 场景含断言，但判定所需的事实未在台账中记载。
   典型形态：某条事实的 `known_by` 为空，且台账没有记录角色如何得知的途径。
   这一档的含义是「判不了」，不是「判错了」。

3. **FAIL** — 场景含断言、证据齐全，且与台账的某条不变量或某条已到期承诺冲突，并能指认具体条目。
   硬要求：必须写出被违反的 `invariants[i]` 或 `commitments[j]` 的 id 与原文片段。写不出 id 的，退回第 2 档。

4. **PASS** — 其余情况。需用一句话说明「最接近的约束为什么未被违反」。

## 二、三条边界说明

- **冲突与缺事实同时成立时，走第 2 档。** 理由是缺事实意味着无法确认冲突是否真实存在，先判「判不了」比先判「判错」保守。
- **PASS 与 NOT_RUN 的分界在断言有无。** 有断言且无冲突才是 PASS；无断言才是 NOT_RUN。
- **FAIL 不得凭空产生。** 没有 id 与原文引用的 FAIL 一律无效，自动降级为 UNDECIDABLE 并计入无效率。

## 三、输出结构（P3）

```json
{
  "3": {
    "verdict": "UNDECIDABLE",
    "anchor_ids": [],
    "missing_fields": ["how_B_learned_F003"],
    "note": "台账未记 B 如何得知木匣内容"
  }
}
```

字段约束：

- `verdict` 取四标签之一
- `anchor_ids` 在 FAIL 时必填，至少一条
- `missing_fields` 在 UNDECIDABLE 时必填，至少一条
- `note` 一句话，不超过 40 字

## 四、验收口径

- 主指标：五模型各 ≥11/12
- hold-out 六场景：每模型 ≥5/6，其中「真 NOT_RUN」（纯环境描写）必须 5/5 仍判 NOT_RUN
- α 只作不降约束（≥0.7529）
- FAIL 的 `anchor_ids` 由脚本核验：id 存在且确实被违反，要求 100% 可复核
- 无效率（FAIL 缺 anchor、UNDECIDABLE 缺 missing_fields）≤20%，超了就回炉改文本

## 五、来源

本版由圆桌会议定案：场景 3 缺事实、场景 10 无断言、场景 12 假设分支，三处错判同源于四标签无互斥与优先级。补丁不新增标签，只排序与加硬要求。
