# 判据 v4：把「缺不缺事实」从判断改成核对

## 为什么要改

v2 与 v3 在两轮实测里来回翻车：

- v2（「缺事实」定义宽松）：命中率 kimi 10/12、mimo 8/12，但两人一致性 α = −0.19。模型把三处硬违规判成「判不了」。
- v3（收紧成三条同时成立）：命中率 mimo 9/12、gemini-4 10/12，两人 α = 0.7473 回到正常，但场景 3（该判「判不了」）两人都判成了 FAIL。

同一把尺子往两边拧都过头。根因不在松紧，在于「缺事实」这件事靠自然语言写不出唯一读法。

## 改法

把这件事从**判断**改成**核对**：

1. 夹具里每个场景新增 `prerequisite_facts` 字段，写明判定这格必须先知道哪些事实，每条标注 `in_ledger`（台账里有没有）与编号。
2. prompt 把这列清单直接展示给裁定者。
3. 判据只做四步照抄：
   - 无断言 → NOT_RUN
   - 前置清单里出现「台账缺失」→ UNDECIDABLE，并写出缺哪条
   - 清单全为「台账已有」且与不变量/承诺冲突 → FAIL，写出被违反条目的编号与原文
   - 其余 → PASS
4. 明确禁止裁定者重新论证「缺不缺」——标注就是依据。

## 这样做的代价与好处

代价：出题方要逐场景写前置事实清单，人工成本上升；清单本身写错，判据就跟着错。

好处：歧义从「模型怎么理解」转移到「清单怎么写」，而清单是可用代码校验、可被第三方复核的。判据不再要求模型做开放式推理。

## 怎么验

同一批 12 场景，mimo-pro 与 gemini-4 各判一遍，比三样：

- 命中率
- 两人一致性 α（衡量可靠性）
- 前置清单被引用的比例（衡量模型有没有真的照表走）

若 α 上到 0.9 以上且命中率不降，说明「把判断改成核对」这条路成立；若 α 高而命中率降，说明清单写错了，要修清单而不是修判据。
